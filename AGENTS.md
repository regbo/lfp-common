# Repository Agent Guide

## Project shape

- This is a Projen-managed Bun and uv monorepo. JavaScript and TypeScript packages live under `packages/js/*`; Python packages and examples live under `packages/py/*`.
- Treat `.projenrc.ts` as the source of truth for project and package metadata, shared dependency versions, TypeScript configuration, tasks, generated documentation, and GitHub workflows.
- Do not hand-edit files marked `Generated by projen`. Change `.projenrc.ts`, run `bun run projen`, and include the synthesized results that belong to the change.
- Consult `docs/llm/UTILITIES.md` and any package-local utility catalog before adding shared helpers. Update the appropriate catalog when introducing a reusable utility.

## Dependencies and commands

- Use Bun for JavaScript and TypeScript dependency management, scripts, builds, and tests. Keep shared external versions in the root workspace catalog and use `catalog:` from packages; use `workspace:*` for sibling packages.
- Use the root uv workspace for Python. Run Python commands through `uv run --locked --package <package>` when practical, and keep shared development dependencies centralized in the root `pyproject.toml`.
- Run `bun run projen` after changing project configuration. Do not replace generated task definitions with package-local drift.

## DRY review

- Before adding or duplicating a helper, type, adapter, or normalization path, query the repository index with `find_similar` and use `implementation_lookup` for known symbols. Prefer an existing shared utility when it owns the same responsibility.
- Before completing substantive code changes, compare newly introduced functions and types with the repository index. Treat semantic similarity as evidence to inspect, not proof of a violation; keep separate implementations when their responsibilities or runtime boundaries genuinely differ.

## Pynect boundaries

- Python is the source of truth for Pynect schemas and handlers; TypeScript clients and types are generated from that contract. Regenerate consumers when the Python contract changes rather than patching generated output.
- Prefer Chanx's built-in handlers, protocol frames, and connection behavior. Add Pynect adaptation only where the underlying API cannot express the required Python-to-TypeScript behavior.
- Preserve the distinction between local execution, the owned stdio worker, and remote transports. Changes to a shared request, streaming, lifecycle, or error path should be checked across every affected transport.

## Verification

- Keep ordinary iteration proportional. Run the narrowest relevant tests plus targeted type checking, linting, formatting checks, code generation, or build steps for the packages changed.
- Do not default to the full monorepo suite for a localized change. Reserve `bun run verify` and broader integration or packed-package checks for releases, release candidates, and changes that affect Projen synthesis, shared configuration, the package graph, release tooling, generated cross-language contracts, or multiple workspaces.
- Before a release, run the full repository verification and any release-specific checks. `bun run release` performs the fixed-version release transaction and pushes the shared tag; the tag-triggered workflow publishes npm and PyPI artifacts before creating the GitHub Release.

## Working safely

- Check `git status` before editing. This repository is often changed by more than one agent at a time; preserve unrelated work and avoid overlapping a dirty central file such as `.projenrc.ts` without first understanding the active changes.
- Keep package names and the shared version consistent with the Projen model. Do not perform package renames, create release tags, publish packages, or alter registry configuration unless the task explicitly calls for it.
